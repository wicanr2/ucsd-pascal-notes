# 從直譯器反推 opcode 表

手上有一份不知道版本的 p-code，想讀懂它。網路上的 opcode 表不能直接用
（見[版本陷阱](../30-opcode-tables/version-traps.md)）。

正解是：**那份程式碼一定附帶自己的直譯器，直譯器的 dispatch 表就是它的 opcode 表**。
這是一手資料，不需要相信任何外部文件。

> 延伸閱讀：[指令編碼](../20-pcode-encoding/instruction-encoding.md)

## 為什麼直譯器一定給得出答案

p-code 不能自己執行，一定有一個直譯器把每個 opcode 對應到一段原生碼。
那個對應關係必須以某種形式存在於直譯器裡，而且**必須是密集的查表**——
每執行一條指令就要查一次，沒有人負擔得起線性搜尋。

所以直譯器裡一定有一張「opcode → 處理常式位址」的表，而且它的形狀很好認：
一段連續的位址常數，長度接近 128。

## 步驟

### 1. 找主迴圈的間接跳躍

從直譯器的進入點往下讀，找「取一個位元組 → 跳到一個算出來的位址」。
UCSD I.5 的 PDP-11 版是這五行：

```asm
SLDCI:  MOV     R0,-(SP)
BACK:   GETNEXT                 ; 取下一個指令位元組到 R0
        BPL     SLDCI           ; 正數（< 128）是短常數，推值就回來
        ASL     R0              ; ×2 當 word 索引
        MOV     XFRTBL(R0),PC   ; 跳到對應的處理常式
```

`MOV <表>(R0),PC` 就是 dispatch。表名 `XFRTBL` 由此得到。

**如果直譯器是機器碼**（68000、6502、x86），這一步用反組譯器做。
在 IDA 裡找的是同一個形狀：一個以位元組值為索引的間接跳躍
（68000 通常是 `move.w (a0,d0.w*2),d1` 之後 `jmp`，或 `jsr ([table,d0.w*4])`）。
找到之後把表的區間標成位址陣列，IDA 會把每個目標函式建出來——
**那些函式就是各個 opcode 的實作，函式體本身說明它做什麼**。

### 2. 對齊表的基底

表的第 0 筆對應哪個 opcode？答案在定址算式裡，不要用猜的。

I.5 的 `XFRTBL = . + 400`（八進位 400 = 256 位元組）配上「opcode 當有號數、
乘 2 當索引」：opcode 128 被視為 −128，×2 = −256，加上 +256 的基底剛好落在表的第 0 筆。
所以**第一筆是 opcode 128**。

這一步錯了，整張表就整體平移，而且平移過的表仍然「看起來合理」——
每個 opcode 都對到某個真實存在的助記符。這種錯誤不會自己浮現。

### 3. 注意保留槽

表裡可能有「保留但不放位址」的槽。I.5 用 `.BLKW n`：

```asm
        .WORD   S2P
        .BLKW   1          ← 這裡是一個空槽，不是零個
        .WORD   LDCN
```

只抓 `.WORD` 會漏掉它，後面每一筆都往前移一格。這是實際踩過的坑：
第一版抄出來的表從 `0x9e` 之後全錯，而它看起來完整無缺。

機器碼版的等價物是「指向同一個 `illegal opcode` 常式的槽」——
連續好幾筆指向同一個位址時，那多半是保留槽而不是真的有那麼多指令。

### 4. 用第二個來源框住範圍

表到哪裡結束？找另一份獨立的東西來對。

I.5 的答案來自官方反組譯器 `CODESTAT`：它的統計迴圈寫 `FOR OP:=128 TO 215`。
而 dispatch 表數到 215 恰好是 88 槽——兩邊吻合，範圍就定了。
216 之後屬於「編號編進 opcode」的短形式，不在主表裡。

沒有第二份文件時，用**表的內容**自己框：處理常式的位址應該落在直譯器的程式碼範圍內，
一旦連續好幾筆落在範圍外，表就結束了。

### 5. 拿實際程式碼驗證

表解出來之後，**不要直接相信它**。挑幾個在目標程式碼裡高頻出現的位元組樣式，
用表解讀看語意通不通。

好的驗證樣式有兩個特徵：出現頻率高，而且**語意已經由別的證據獨立確定**。
例如某個樣式總是出現在「開啟某個畫面」之前，而該畫面的資料結構已經解出來了——
若用表解讀出來是「字串索引」，那就是表錯了，不是資料錯了。

## 這個方法的邊界

- **直譯器可能不只一張表。** 比較運算、字串運算、系統呼叫常有各自的子表，
  由主表的某一格帶進去。I.5 用 `XFRTBL+40.` 這個偏移進比較子表。
- **有些 opcode 沒有表項。** 短常數與短載入直接由 opcode 值本身帶運算元，
  它們在主迴圈就被分流掉，不經過 dispatch 表。表裡找不到它們是正常的。
- **表給的是「跳到哪」，不是「做什麼」。** 助記符是處理常式的標籤名；
  組語版通常有名字可用，機器碼版只有位址，語意要自己讀函式體。

## 一個實例的現況

SunDog（1985，Atari ST）的遊戲邏輯是 UCSD IV.x 的 p-code，
磁碟上同時有 `SYSTEM.STARTUP`（遊戲程式碼）與 `SYSTEM.INTERP`（68000 寫的直譯器，11776 位元組）。

已知的實測片段（由該遊戲自身的資料結構獨立驗證）：

| 位元組 | 語意 |
|---|---|
| `9a <層級> <變長編號>` | 載入全域的值 |
| `9b <層級> <變長編號>` | 取全域的位址 |
| `d9 <層級> <變長編號>` | 存入全域 |
| `ef <n>` | 呼叫同段第 n 號程序 |
| `ee` | 陣列索引 |

變長編號的規則與 I.5 相同（最高位為 1 就吃第二個位元組），
但 opcode 分配完全不同。**完整的表尚未解出**——`SYSTEM.INTERP` 的 dispatch 表還沒反組譯。
按上面的步驟做，那是下一步。
