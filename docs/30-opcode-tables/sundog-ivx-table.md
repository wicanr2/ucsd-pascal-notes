# 實例：解出一份 1985 年 68000 直譯器的 opcode 表

拿[五步反推法](../40-re-workflow/recover-opcode-table.md)實跑一次。
目標是 SunDog（1985，Atari ST）磁碟上的 `SYSTEM.INTERP`：68000 機器碼，11776 位元組，
版權字串寫「Copr. (c) 1981 Tallgrass Technologies」。

結論先講：**它的分配與 [UCSD I.5](version-traps.md) 沒有一格相同**，
而且短形式的切法完全不一樣。

## 第 1 步：找 dispatch

在 IDA 裡以 68000 raw binary 載入（`idat -A -p68000`），先掃 68000 的跳躍 opcode。
`0x4E??` 這一族裡，變址跳躍 `4EF0`–`4EF7`（`jmp d8(an,ix)`）只出現 3 次——
其中一次就是主迴圈：

```
00de: 70 00        moveq  #0,d0
00e0: 10 1c        move.b (a4)+,d0        ; 取 opcode，a4 是 p-code 指標
00e2: d0 40        add.w  d0,d0           ; ×2 當 word 索引
00e4: 3e 3b 00 06  move.w (6,pc,d0.w),d7  ; 查表
00e8: 4e f3 70 00  jmp    (0,a3,d7.w)     ; 跳到 a3 + 表值
```

同一次掃描還給了另一個有用的數字：`jmp (a5)`（`4ED5`）出現 **109 次**。
那是各個處理常式的結尾——回主迴圈。所以這份直譯器大約有一百多個常式，
與一張 256 項的表相符。

## 第 2 步：對齊基底

`move.w (6,pc,d0.w),d7` 的 PC 相對基底是指令位址 `0xe4` 加 2（68000 的 PC 相對以
擴充字位址為準）再加位移 6，得 **`0xec`**。索引是 opcode×2，所以**表的第 0 項對應 opcode 0**，
256 項共 512 位元組，`0xec`–`0x2ec`。

表值是相對 a3 的位移。a3 是不是載入基底？用內容驗證：前 32 項都是 `00d8`，
而 `0xd8` 處是

```
00d8: e2 48        lsr.w  #1,d0      ; 把 ×2 除回來
00da: 3f 00        move.w d0,-(sp)   ; 推上堆疊
00dc: 4e d5        jmp    (a5)
```

一個「還原 opcode 值並推堆疊」的常式，正是短常數該有的樣子。
**a3 就是載入基底，表值可以直接當檔案內位移讀。**

## 第 3 步：保留槽

這份表沒有 `.BLKW` 式的空槽，但有等價物：**45 個 opcode 指向同一個 `0x304`**，
而那裡是

```
0304: 70 0b        moveq #$B,d0      ; 錯誤碼 11
0306: 60 14        bra.s loc_31C     ; 跳錯誤處理（印訊息後中止）
```

指向錯誤處理的槽就是這一版的「未使用」。它們集中在 `0x40`–`0x5f`、`0xaa`、`0xaf`、
`0xf5`–`0xff`——**中間那一段留白很值得注意**，見下面。

## 第 4 步：範圍

表滿 256 項，沒有提早結束。107 個相異目標，其中 11 個被多個 opcode 共用、96 個是專屬。

## 第 5 步：驗證

拿三個在遊戲程式碼裡高頻出現、而且語意已由該遊戲自己的資料結構獨立確定的位元組來對：

| opcode | 表值 | 常式 | 是否與實測相符 |
|---|---|---|---|
| `0x9a` | `0x0690` | `bsr sub_668` / `move.w (a6,d7.l),-(sp)` | 載入全域的值 ✓ |
| `0x9b` | `0x0698` | `bsr sub_668` / `move.w d7,-(sp)` | 取全域的位址 ✓ |
| `0xd9` | `0x069e` | `bsr sub_668` / `move.w (sp)+,(a6,d7.l)` | 存入全域 ✓ |

三個都對上，而且三個常式在檔案裡相鄰（`0x690`/`0x698`/`0x69e`）——
「載入值／載入位址／存入」寫成三兄弟是很自然的實作順序，這本身也是旁證。

## 解出來的短形式

d0 進處理常式時是 **opcode×2**，所以每個常式開頭的 `subi.w` 常數直接洩漏了該群的編號起點。

| opcode | 目標 | 語意 |
|---|---|---|
| `0x00`–`0x1f` | `0x00d8` | 短常數 0–31 |
| `0x20`–`0x2f` | `0x0534` | 短載入區域變數 1–16（`move.w 8(a0,d0.l),-(sp)`） |
| `0x30`–`0x3f` | `0x059c` | 短載入，另一層基底 a1（`move.w 8(a1,d0.l),-(sp)`） |
| `0x40`–`0x5f` | `0x0304` | 未使用（32 個） |
| `0x60`–`0x67` | `0x0554` | 取區域變數位址 1–8（算 `a0+n−a6`） |
| `0x68`–`0x6f` | `0x057c` | 存入區域變數 1–8（`move.w (sp)+,8(a0,d0.l)`） |
| `0x70`–`0x77` | `0x0ed4` | 短呼叫 1–8（先把 a4 存進 `$1B7C(a3)`） |
| `0x78` | `0x06a6` | 間接載入偏移 0 |
| `0x79`–`0x7f` | `0x06ae` | 間接載入偏移 1–7 |

## 與 UCSD I.5 的差別

| | UCSD I.5（1978，PDP-11） | 這一份（1981，68000） |
|---|---|---|
| 短常數 | `0x00`–`0x7f`，**128 個** | `0x00`–`0x1f`，**32 個** |
| 短載入區域變數 | `0xd8`–`0xe7`（16 個） | `0x20`–`0x2f`（16 個） |
| 短載入全域 | `0xe8`–`0xf7`（16 個） | — |
| 短存入區域變數 | 無 | `0x68`–`0x6f`（8 個） |
| 取區域變數位址 | 無短形式 | `0x60`–`0x67`（8 個） |
| 短呼叫 | 無 | `0x70`–`0x77`（8 個） |

I.5 把低半部整個給了常數；這一份只給 32 個，省下來的編碼拿去做**短存入、取位址、短呼叫**。

這不是隨意的改動。想一下 Pascal 程式的實際樣子：常數大於 31 的情況遠少於「對區域變數賦值」
與「呼叫本段的另一支程序」。I.5 那 96 個用不太到的常數編碼，換成三種新的短形式更划算。
**同一個密度原則，在不同的統計資料上得到不同的答案。**

`0x40`–`0x5f` 那 32 個留白也在這個脈絡下說得通：它是短常數區與短載入區之間的預留，
一整段連續、對齊 32 的邊界，形狀像是「留給未來的短形式」而不是零星的廢棄碼。

## 附帶證實的一件事

運算元解碼器 `sub_668` 把兩件事一次講清楚：

```
0668: moveq  #0,d0
066a: move.b (a4)+,d0        ; 層級（lex level）
066c: add.w  d0,d0
066e: add.w  $1B8A(a3),d0    ; 查層級表
0672: move.w (a6,d0.l),d7    ; 取該層的 frame
0676: move.w (a6,d7.l),d7    ; 靜態鏈
067a: moveq  #0,d0
067c: move.b (a4)+,d0        ; 變長編號的第一個位元組
067e: bpl.s  loc_688         ; 最高位 0 → 就是它本身
0680: andi.b #$7F,d0         ; 最高位 1 → 去掉旗標
0684: lsl.w  #8,d0
0686: move.b (a4)+,d0        ; 吃第二個位元組
loc_688:
0688: add.w  d0,d0           ; ×2（word 編號換成位元組偏移）
068a: add.w  d0,d7
068c: addq.w #8,d7           ; +8（活動記錄標頭）
068e: rts
```

第一，**變長編碼與 I.5 一模一樣**（`bpl` 判最高位、`andi #$7F` 後左移八位再吃一個位元組）。
編碼慣例跨版本穩定，這是又一個例子。

第二，最後兩行 `add.w d0,d0` 加 `addq.w #8,d7` 就是「word 編號 × 2 + 8 等於 a6 相對位元組」
這條換算的出處。逆向 SunDog 時這條式子是從觀察歸納出來的；直譯器碼把它變成可讀的機制。

## 還沒做的

96 個專屬 opcode 的語意還沒逐條讀。表本身（值→常式位址）與上面列出的結構已經確立，
剩下的是把每個常式的 68000 碼讀成語意。
