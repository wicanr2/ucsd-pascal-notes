# opcode 表與版本陷阱

p-code 的**指令編碼慣例**跨版本穩定，**opcode 的數值分配不穩定**。
把兩者混為一談，會解出一份自洽但完全錯誤的反組譯。

> 延伸閱讀：[指令編碼](../20-pcode-encoding/instruction-encoding.md)、
> [從直譯器反推 opcode 表](../40-re-workflow/recover-opcode-table.md)

## UCSD Pascal I.5 的表（1978，PDP-11）

下表逐槽取自官方直譯器 `mainop.mac` 的 dispatch 表 `XFRTBL`。
兩個獨立來源交叉驗證了它的範圍：

- `XFRTBL = . + 400`（八進位 400 = 256 位元組 = 128 word），配 `ASL R0` 的負索引定址，
  第一筆對應 opcode 128。
- 官方反組譯器 `CODESTAT` 的統計迴圈寫的是 `FOR OP:=128 TO 215`——主表恰好 88 槽。

抄表時最容易錯的地方是 `.BLKW n`（保留 n 個槽而不放位址）。它有兩層：

- **位移**：只抓 `.WORD` 會讓後面整段往前擠，得到一張看起來很完整、從中間開始全錯的表。
- **那些槽不是空的**：`mainop.mac` 與 `procop.mac` 有同名的 `.CSECT TABLES`，連結時疊在
  一起，`procop.mac` 那份用自己的 `.BLKW` 對齊、把程序呼叫族填進 `mainop.mac` 留的空格。
  八格全部有指令——上表的 `CSP`、`RNP`、`CIP`、`RBP`、`CBP`、`CXP`、`CLP`、`CGP` 就是它們。
  逐條語意見 [I.5 各 opcode 的語意](i15-opcode-semantics.md)。

## 陷阱：這張表不能拿去讀別版的程式碼

把 I.5 的表套到 1985 年 Atari ST 版 SunDog（UCSD IV.2.1）的 p-code 上，逐格都對不上：

| 位元組 | I.5 說是 | 該檔實測是 | |
|---|---|---|---|
| `0x9a` | `STO`（把值存進位址） | 載入全域的**值** | 不符 |
| `0x9b` | `IXS`（字串索引） | 取全域的**位址** | 不符 |
| `0xd9` | `SLDL 2`（載入區域變數 2） | **存入**全域 | 不符 |
| `0xc5` | `GRTI`（整數大於） | 疑似記憶體複製 | 不符 |
| `0xee` | `SIND 6` | 陣列索引 | 不符 |
| `0xef` | `SIND 7` | 呼叫同段程序 | 不符 |

實測那一欄不是猜的。以 `0x9b` 為例：`9b 04 87 73` 這個樣式在該遊戲的程式碼裡
反覆出現在「取視窗表第 n 筆」的位置上，而 `0x773` 這個全域編號獨立地被視窗表的
資料結構驗證過。若照 I.5 讀成 `IXS`，整段語意會散掉。

**六個裡沒有一個對上**，所以這不是「大致相同、少數例外」，是兩套不同的分配。

## 為什麼會變

看起來像亂改，其實有原因（先重建它再判斷）：

1. **主表只有 88 槽，而且已經全滿。** `0x80`–`0xd7` 一格不剩。
   IV.x 要加東西（單位、分離編譯、更完整的集合與長整數、並行），非重排不可。
2. **不同 CPU 的最佳分配不同。** dispatch 是 `ASL` 加查表，但短形式那幾段是展開的直碼；
   哪些指令值得放進短形式，取決於該 CPU 上哪一種定址便宜。PDP-11 與 68000 的答案不一樣。
3. **短形式的邊界也會動。** I.5 給區域變數 16 個短槽；如果某一版發現全域變數更熱，
   把槽位重新分配是最直接的優化。

所以正確的做法不是找「一張權威的 UCSD opcode 表」——沒有這種東西，只有「某一版的表」。
方法見[從直譯器反推 opcode 表](../40-re-workflow/recover-opcode-table.md)。

## 第三個座標：IV.0 的官方表

SofTech 在 1981 年的《Internal Architecture Guide》附錄 VI.B 印了 IV.0 的完整 opcode 表
（[摘譯](../50-iv-internals/appendix-opcodes.md)）。它跟前面兩張表放在一起，短形式的分配是：

| 短形式 | I.5（1978） | IV.0 官方（1981） | IV.2.1 實測（1985） |
|---|---|---|---|
| `SLDC` | `0x00`–`0x7f`（128 個） | `0x00`–`0x1f`（32 個） | `0x00`–`0x1f` |
| `SLDL` | `0xd8`–`0xe7` | `0x20`–`0x2f` | `0x20`–`0x2f` |
| `SLDO` | `0xe8`–`0xf7` | `0x30`–`0x3f` | `0x30`–`0x3f` |
| `SLLA` | 無 | `0x60`–`0x67` | `0x60`–`0x67` |
| `SSTL` | 無 | `0x68`–`0x6f` | `0x68`–`0x6f` |
| `SCXG` | 無 | `0x70`–`0x77` | `0x70`–`0x77` |
| `SIND` | `0xf8`–`0xff` | `0x78`–`0x7f` | `0x78`–`0x7f` |

兩件事同時成立：

- **I.5 → IV.0 之間，短形式整個重排。** `SLDC` 從 128 格砍到 32 格，省下來的空間開給
  `SLLA`、`SSTL`、`SCXG` 三個新的短形式。上一節說「短形式的邊界也會動」，這是它的實際樣子；
  手冊沒有寫為什麼要這樣改，所以那三個原因仍是推測。
- **IV.0 → IV.2.1 之間，短形式一格沒動。** SunDog 的表是從它自己的直譯器解出來的，
  當時手上沒有這份手冊；解完之後拿官方表對，逐格吻合。

短形式以外的主表（`0x80`–`0xff`）後來也整段對過了，同樣重合：IV.0 表列出的 211 個指令
與 IV.2.1 有處理常式的 211 個槽逐格相同，兩邊「沒有指令」的 45 格也在同樣位置。
過程與證據見[逐格對照：IV.0 官方表 × IV.2.1 dispatch 表](iv0-vs-iv21.md)。

語意層也驗過了：98 個處理常式逐條讀完，全部與 IV.0 的文字定義相符
（見[逐條驗證](iv21-routine-audit.md)）。所以**讀 IV.2.1 的 p-code 可以直接用 IV.0 的表**，
編號與語意都可信，不必再從直譯器重解一次。

這個結論只涵蓋 IV.0 → IV.2.1 這一段。跨版本的數值分配沒有保證，
換一份來歷不明的 p-code，仍然要用它自己的位元組驗過。

## 跨版本仍然可信的部分

版本會動的是數值，不動的是這幾條結構性事實。它們可以當作解新版表時的起手假設：

- **opcode 一律單一位元組。** 三個版本都是（IV.0 手冊 p.50 明寫）。
- **運算元的變長規則**：最高位為 0 是一個位元組，為 1 就再吃一個。
  I.5 的 `CODESTAT`、IV.0 手冊 p.46、SunDog 直譯器的解碼器三邊逐位元一致。
- **短形式這個機制存在**：一定有一段 opcode 把運算元編進值本身，用來壓縮最常見的
  幾種載入與存取。
- **執行期錯誤碼**。I.5 的 `macros.mac` 定義的常數（1 範圍檢查、6 除零、11 未實作、
  12 浮點、13 字串太長…）與 1985 年 IV.2.1 直譯器的錯誤入口逐項相同，七年沒動。
  對照見 [I.5 各 opcode 的語意](i15-opcode-semantics.md#錯誤碼在兩版之間沒有變)。
- **每個程序的碼結尾有一個明確的結束標記**。I.5 是 `XIT`（214）：官方反組譯器
  `CODESTAT` 看到它就 `DONEPROC:=TRUE`，而直譯器對它的實作是 `HALT`——
  **對反組譯器是邊界標記，對直譯器是陷阱**。真正的返回指令是 `RNP`／`RBP`。

反過來，下面這幾件事**不能**當起手假設，看起來像通則其實是 I.5 的個別選擇：

| 看起來像通則 | 實際上 |
|---|---|
| `0x00`–`0x7f` 全是短常數 | 只有 I.5 這樣。IV.0 起 `SLDC` 只佔 `0x00`–`0x1f` |
| 短形式放在 opcode 的高段 | I.5 放高段，IV.0 起整批搬到低段 |
| 哪些指令有短形式 | I.5 有四種，IV.0 有七種 |

起手假設要用該檔案自己的位元組驗證過才算數——**它是縮小搜尋範圍的工具，不是結論**。
