# opcode 表與版本陷阱

p-code 的**指令編碼慣例**跨版本穩定，**opcode 的數值分配不穩定**。
把兩者混為一談，會解出一份自洽但完全錯誤的反組譯。

> 延伸閱讀：[指令編碼](../20-pcode-encoding/instruction-encoding.md)、
> [從直譯器反推 opcode 表](../40-re-workflow/recover-opcode-table.md)

## UCSD Pascal I.5 的表（1978，PDP-11）

下表逐槽取自官方直譯器 `mainop.mac` 的 dispatch 表 `XFRTBL`。
兩個獨立來源交叉驗證了它的範圍：

- `XFRTBL = . + 400`（八進位 400 = 256 位元組 = 128 word），配 `ASL R0` 的負索引定址，
  第一筆對應 opcode 128。
- 官方反組譯器 `CODESTAT` 的統計迴圈寫的是 `FOR OP:=128 TO 215`——主表恰好 88 槽。

抄表時最容易錯的地方是 `.BLKW n`（保留 n 個槽而不放位址）。只抓 `.WORD` 會讓後面
整段位移，得到一張看起來很完整、從中間開始全錯的表。

## 陷阱：這張表不能拿去讀別版的程式碼

把 I.5 的表套到 1985 年 Atari ST 版 SunDog（UCSD IV.x）的 p-code 上，逐格都對不上：

| 位元組 | I.5 說是 | 該檔實測是 | |
|---|---|---|---|
| `0x9a` | `STO`（把值存進位址） | 載入全域的**值** | 不符 |
| `0x9b` | `IXS`（字串索引） | 取全域的**位址** | 不符 |
| `0xd9` | `SLDL 2`（載入區域變數 2） | **存入**全域 | 不符 |
| `0xc5` | `GRTI`（整數大於） | 疑似記憶體複製 | 不符 |
| `0xee` | `SIND 6` | 陣列索引 | 不符 |
| `0xef` | `SIND 7` | 呼叫同段程序 | 不符 |

實測那一欄不是猜的。以 `0x9b` 為例：`9b 04 87 73` 這個樣式在該遊戲的程式碼裡
反覆出現在「取視窗表第 n 筆」的位置上，而 `0x773` 這個全域編號獨立地被視窗表的
資料結構驗證過。若照 I.5 讀成 `IXS`，整段語意會散掉。

**六個裡沒有一個對上**，所以這不是「大致相同、少數例外」，是兩套不同的分配。

## 為什麼會變

看起來像亂改，其實有原因（先重建它再判斷）：

1. **主表只有 88 槽，而語言在長大。** I.5 已經用掉 `0x80`–`0xd7` 幾乎全部，只剩六個保留槽。
   IV.x 要加東西（單位、分離編譯、更完整的集合與長整數），非重排不可。
2. **不同 CPU 的最佳分配不同。** dispatch 是 `ASL` 加查表，但短形式那幾段是展開的直碼；
   哪些指令值得放進短形式，取決於該 CPU 上哪一種定址便宜。PDP-11 與 68000 的答案不一樣。
3. **短形式的邊界也會動。** I.5 給區域變數 16 個短槽；如果某一版發現全域變數更熱，
   把槽位重新分配是最直接的優化。

所以正確的做法不是找「權威的 UCSD opcode 表」，是**對著手上那一份直譯器把表解出來**。
方法見[從直譯器反推 opcode 表](../40-re-workflow/recover-opcode-table.md)。

## 跨版本仍然可信的部分

版本會動的是數值，不動的是這幾條結構性事實。它們可以當作解新版表時的起手假設：

- `0x00`–`0x7F` 是短常數（值即 opcode）。這是密度設計的核心，改掉它等於重做整個編碼。
- 運算元的變長規則（最高位為 1 就吃第二個位元組）。
- 高段 opcode 保留給「把變數編號編進 opcode」的短形式。
- 每個程序的結尾有一個明確的退出指令（I.5 是 `XIT`，`CODESTAT` 用它判斷程序邊界）。

起手假設要用該檔案自己的位元組驗證過才算數——**它是縮小搜尋範圍的工具，不是結論**。
