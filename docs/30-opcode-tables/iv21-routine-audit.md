# 逐條驗證：98 個處理常式對上 IV.0 的定義

[逐格對照](iv0-vs-iv21.md)確立了 IV.2.1 與 IV.0 的 **opcode 編號**相同，但那是集合層面的
結論——編號相同不保證語意相同。這一篇把語意也驗了。

> 延伸閱讀：[逐格對照：IV.0 官方表 × IV.2.1 dispatch 表](iv0-vs-iv21.md)｜
> [實例：解出一份 1985 年 68000 直譯器的 opcode 表](sundog-ivx-table.md)｜
> [IV 版指令逐條語意](../50-iv-internals/instruction-set-details.md)

結論先講：**98 個常式逐條讀完，全部與 IV.0 的文字定義相符，沒有一條不符。**
所以拿 IV.0 的手冊讀 IV.2.1 的 p-code，不只編號可信，語意也可信。

順帶推翻了三個 repo 自己先前的斷言——都寫在最後一節。

## 方法

這一步是**驗證**不是解謎：編號既然已經確定，就拿 IV.0 對每個 opcode 的文字定義當假設，
去讀那個 opcode 的 68000 處理常式，看碼做的事情是不是那件事。

1. **取反組譯**。`tools/dump-routines.py` 是 IDAPython 腳本，在 IDA 裡對 dispatch 表的
   每個目標位址強制反組譯，讀到 `jmp (a5)`（回主迴圈）、`rts` 或無條件跳躍為止：

   ```
   docker run --rm --network none -u "$(id -u):$(id -g)" -v "$WORK:/work" -w /work \
     ida-pro-9.4-idapython:locked-v1 \
     idat -A -p68000 -S"/work/dump-routines.py /work/routines.json" SYSTEM.INTERP
   ```

   107 個相異目標全部反組譯成功，沒有一個撞到指令數上限。

2. **配對**。`tools/routine-audit.py --pairs` 把每個常式與 IV.0 的助記符、官方說明並排。

3. **判讀**。扣掉錯誤常式（45 格）、浮點 fault（16 格）與短形式群常式
   （95 格，已在[實例篇](sundog-ivx-table.md)解過），剩下 98 個常式逐一讀。

正對照：先拿[逐格對照](iv0-vs-iv21.md)裡人工解碼過的四個常式比對 IDA 的輸出，
逐位元組一致，包括 `move.w (sp)+,8(a0,d0.l)` 這種索引寬度。

## 順帶解出來的暫存器分工

讀 98 個常式最有用的副產品，是把這份直譯器的暫存器約定整理出來。
每一條都由多個常式交叉印證，不是單點推測：

| 暫存器 | 用途 | 證據 |
|---|---|---|
| `a0` | 目前活動記錄（MP） | `8(a0,d0.l)` 存取區域變數（`LDL`/`STL`/`SLDL`）；`CPL` 拿 `a0` 當靜態鏈 |
| `a1` | 本段全域資料基底（就是手冊的 `BASE`） | `8(a1,d0.l)` 存取全域（`LDO`/`SRO`）；`CPG` 拿 `a1` 當靜態鏈 |
| `a2` | 目前 code segment 的基底 | `$C(a2)` 是 byte sex 指示字、`$E(a2)` 是常數池指標——對得上 Figure 1 的段頭欄位順序 |
| `a3` | 直譯器自己的變數區 | `$1B7C(a3)` 存 p-code 指標、`$1B8E(a3)` 存目前段號 |
| `a4` | p-code 指標（IPC） | 到處都是 `move.b (a4)+,d0` 取運算元 |
| `a5` | 主迴圈位址 | 每個常式結尾 `jmp (a5)` |
| `a6` | word 位址的基準 | `(a6,d7.l)` 把 p-machine 的 word 位址轉成實體位址 |
| `d0` | 進常式時是 **opcode×2** | 主迴圈 `add.w d0,d0` 之後才 dispatch；短形式常式靠它算編號 |

`a1` 就是 `BASE` 這一條，補上了[程序呼叫](../10-p-machine/procedure-call.md)那篇留下的
待查證項：手冊沒有明寫 `BASE` 與 TIB 欄位 `BP` 的關係，但實作把「全域資料基底」與
「`CPG` 的靜態鏈」用同一個暫存器，兩者是同一個東西這點在這份直譯器裡是確定的。

## 值得單獨看的幾條

98 條都相符，但其中幾條帶來的資訊超出「相符」本身。

**`CPL` 與 `CPG` 印證了靜態鏈的推導。** [程序呼叫](../10-p-machine/procedure-call.md)那篇從
手冊文字推出「`CPL` 的靜態鏈是呼叫者自己的框、`CPG` 的是 `BASE`」。實作是兩行：

```
0e64: 2a08         move.l  a0,d5      ; CPL：靜態鏈 = a0 = 目前活動記錄
0e74: 2a09         move.l  a1,d5      ; CPG：靜態鏈 = a1 = 全域基底
```

`CPG` 的常式只有兩條指令——設好 `d5` 就 `bra` 進 `CPL` 的共同路徑。
**兩個呼叫指令的差別，實作起來就是一個暫存器編號的差別。**

**`Ref_Count` 有位元組證據。** 手冊 p.34–35 說 SIB 的 `Ref_Count` 是「未完成的跨段呼叫數，
段外呼叫段內時加一、段內返回段外時減一」。實作把這兩半分別放在 `CXL` 與 `RPU`：

```
0ece: 52767804     addq.w  #1,4(a6,d7.l)    ; CXL 跨段呼叫進去，加一
1040: 53767804     subq.w  #1,4(a6,d7.l)    ; RPU 跨段返回出來，減一
```

同一個偏移 `4(...)`，一加一減，成對。[segment 那篇](../10-p-machine/segment-and-environment.md)
講 SIB 三個計數欄位的推導，這裡是它的實作面。

**`NOP` 的處理常式就是主迴圈。** dispatch 表第 `0x9c` 格指向 `0x00de`，而 `0x00de` 正是
取下一個 opcode 的主迴圈入口。不做任何事的最省寫法不是寫一個只有 `jmp (a5)` 的常式，
是**讓 dispatch 直接指回 fetch**——省一次跳躍。

**`CXG` 的內嵌表有一個手冊沒寫的上限。** 手冊 p.66 說 segment 號為 1 時程序碼可能內嵌在
直譯器裡、由直譯器表格給出位置。實作除了比對段號，還檢查程序號：

```
0eea: 0c400001     cmpi.w  #1,d0        ; 段號是 1 嗎
0eee: 66ae         bne.s   loc_E9E      ; 不是就走一般路徑
0ef2: 1214         move.b  (a4),d1      ; 偷看程序號（不前進）
0ef4: 0c410030     cmpi.w  #$30,d1      ; 大於 0x30 就走一般路徑
0ef8: 62a4         bhi.s   loc_E9E
```

**內嵌表只涵蓋程序號 1..0x30（48）**，超過就退回一般的跨段呼叫。
手冊只說「可能內嵌」，沒說範圍；這是這份直譯器自己的實作決定。
注意第三行用 `move.b (a4)` 而不是 `(a4)+`——**先偷看再決定**，因為走一般路徑時
還要由那條路徑自己去讀這個位元組。

**執行期錯誤碼可以從觸發點反推。** 幾個常式直接跳進錯誤處理的不同入口，
於是錯誤碼與語意配對出來：

| 錯誤碼 | 入口 | 由誰觸發 | I.5 的常數名 |
|---|---|---|---|
| 1 | `0x02ec` | `SRS`、`CHK`、`CSTR` 的範圍檢查 | `INVNDX` |
| 2 | `0x02f0` | — | `NOPROC` |
| 5 | `0x02f4` | — | `INTOVR` |
| 6 | `0x02f8` | `DVI`、`MODI` 的除零檢查 | `DIVZER` |
| 8 | `0x02fc` | — | `UBREAK` |
| 10 | `0x0300` | — | `UIOERR` |
| 11 | `0x0304` | 45 個未使用的槽 | `NOTIMP` |
| 12 | `0x0308` | 16 個浮點指令 | `FPIERR` |
| 13 | `0x030c` | `CSP`、`ASTR` 的長度檢查 | `S2LONG` |
| 16 | `0x0310` | `BPT` | —（I.5 的表最大到 15） |

這些入口是連續的九組 `moveq #n,d0` / `bra.s`，全部跳到 `0x031c` 的共同處理。
最右欄來自 1978 年 I.5 的 `macros.mac`——那份原始碼直接定義了這些常數，
與這裡從觸發點反推的語意逐項對上，見
[I.5 各 opcode 的語意](i15-opcode-semantics.md#錯誤碼在兩版之間沒有變)。
**錯誤碼是跨版本穩定的那一類東西。**

**`SRS` 的範圍上限逐位元組對上。** 手冊說子範圍集合的兩端必須落在 `[0..4079]`，
實作是 `cmpi.w #$FF0,d0` 加 `bcc`——`0xFF0` 就是 4080，大於等於就跳錯誤。

**`SLOD` 與 `SCPI` 兩對共用常式的算法一模一樣。** 都是還原 opcode 再減一個常數：

```
05ec: e248 0440 00ac   lsr.w #1,d0 / subi.w #$AC,d0   ; 0xad→1、0xae→2
0e78: e248 0440 00ee   lsr.w #1,d0 / subi.w #$EE,d0   ; 0xef→1、0xf0→2
```

[逐格對照](iv0-vs-iv21.md)當時只從「兩格指向同一個位址」推測它們靠 opcode 值分辨，
這裡是那個推測的直接證據。

## 三個被推翻的斷言

**一、`LDP`/`STP`/`IXP` 的運算元順序沒有與手冊相反。**
`PLAN.md` 的待辦一直寫著「SunDog 那版的運算元順序與手冊相反」。實測不成立：

```
08c2: 301f  move.w (sp)+,d0    ; TOS   = 欄位最右 bit 編號
08c4: 7210  moveq  #$10,d1
08c6: 925f  sub.w  (sp)+,d1    ; TOS-1 = 欄位位元數（算成 16 − n）
08c8: 3e17  move.w (sp),d7     ; TOS-2 = 該 word 的位址
```

三個值的次序與手冊 `Pack-ptr` 的定義（TOS 是最右 bit 編號、TOS-1 是位元數、
TOS-2 是位址）逐項相同。`IXP` 產生的堆疊格式也正是這一個。詳見
[packed 欄位](../20-pcode-encoding/packed-fields.md)。

**二、`SCXG` 的運算元順序也沒有相反。** 這一條是[逐格對照](iv0-vs-iv21.md)寫的，
而它是把上一條的說法誤植到 `SCXG` 上。實作 `subi.w #$6F,d0` 從 opcode 算出段號、
程序號從 `(a4)+` 讀，與手冊「segment 號由 opcode 指定（1–8），UB 是程序號」一致。

**三、`0x78` 的助記符是 `SIND0` 不是 `SIND1`。**
這是工具的 bug，不是判讀錯誤：`dispatch-crosstab.py` 展開範圍寫法時把起編寫死成 1，
而手冊裡 `SIND` 是 `SIND0 … SIND7`（`SLDL` 卻是 `SLDL1 … SLDL16`）。
只有 `SIND` 這一族受影響，共 8 格。修正後重跑[逐格對照](iv0-vs-iv21.md)，
211 = 211 的結論不變——**那個 bug 只動到標籤，不動到集合比對**。

同一份解析邏輯當時被抄成兩份，兩份都要修才算修完；現在 `routine-audit.py` 直接
沿用 `dispatch-crosstab.py` 的解析，不再有第二份。

## 邊界

- 「相符」的判準是**這個常式做的事情與那句官方定義描述的是同一件事**，不是逐位元的
  形式驗證。定義本身含糊的地方（例如 `LDC` 的 `B+20` 與 `UB_2` 對不上，
  見[逐條語意](../50-iv-internals/instruction-set-details.md)的註）不因為常式看起來合理
  就當作釐清了。
- 反組譯讀到常式的第一個出口為止。`RPU`、`CXG`、`LDC` 這類有分岔的常式，
  另一條路徑沒有全部讀完——判定依據是主路徑加上關鍵分支，不是全路徑覆蓋。
  [實例篇](sundog-ivx-table.md#一個會讓語意讀錯的陷阱)記過只讀快速路徑會出錯，
  這裡的作法是快速路徑與一般路徑都看，但更深的巢狀分支沒有展開。
- 這 98 條是 IV.2.1 的一份實作。相符只能說明這份直譯器照手冊做，
  不能推廣成「IV.2.1 這個版本的規格等於 IV.0」。
